+ Directory-only modules root
- src/modules/ contains only module directories plus optional src/modules/index.ts.
- No functional *.ts/*.js files at src/modules/ root.

+ One public entrypoint per module
- The only public surface of a module is src/modules/<module>/index.ts.
- Anything not exported from that index.ts is non-public.

+ No sub-APIs (strict)
- A sub-API is any public surface other than src/modules/<module>/index.ts, including:
  - deep imports into a module (../<module>/<path>)
  - importing module-local barrel files or subdirectory index files from outside the module
  - deep re-exports that expose non-canonical paths, even if they only re-export other files
- After enforcement, the only legal cross-module import target is ../<module>.

+ Internal encapsulation
- Modules use src/modules/<module>/internal/** for private implementation.
- internal/** must never be imported from outside the owning module.

+ Import style uniformity
- Intra-repo imports use directory specifiers only.
- No trailing slashes in import paths.
- No explicit index imports.

+ Canonical ownership
- Each exported symbol has exactly one owning module.
- All other modules consume it only via the owner module’s index.ts.

+ Duplication handling
- Shared functionality must not be duplicated across modules.
- Resolution is always one of:
  - centralize in the existing owner module
  - promote into a new root module
  - keep internal and remove cross-module usage

+ Promotion
- If a cohesive surface is used by multiple modules, it becomes a new root module:
  src/modules/<new-module>/index.ts
- The new module follows all rules above:
  - single entrypoint
  - no sub-APIs
  - internal/** private
  - no compat or legacy exports or alternate names
- All consumers rewrite imports to ../<new-module>.

+ Re-export constraints
- src/modules/index.ts, if present, re-exports only module entrypoints (../<module>), never deep paths.
- Module index.ts files must not re-export deep paths from other modules.

+ Enforced boundaries
- Lint or build fails on:
  - cross-module deep imports (../<module>/<path>)
  - imports into */internal/*
  - trailing-slash import specifiers
  - explicit index file imports
  - deep re-exports that create alternate public surfaces

+ Module naming conventions
- Module directory names use kebab-case.
- Names are domain-oriented, not implementation-oriented.
- Avoid generic buckets like shared, common, utils unless tightly scoped and owned.

+ File naming conventions
- File names use kebab-case and express responsibility.
- Avoid redundant prefixes inside a module.
- One concept, one file name, no aliases.

+ Symbol naming conventions
- Public APIs use named exports as the default.
- No public default exports.
- No legacy or compat export names.

+ index.ts uniformity
- index.ts defines the public API only.
- index.ts contains no business logic.
- Exports are explicit and minimal.

+ Module internal structure uniformity
- Consistent pattern within each module:
  - index.ts (public API)
  - internal/** (private)
  - types.ts and constants.ts as needed
  - tests follow one consistent convention repo-wide

+ Dependency direction uniformity
- Each module’s allowed dependencies are declared and enforced.
- No upward dependencies and no cycles between modules.

+ API surface minimization
- Export the minimum needed.
- Treat every export as a contract requiring justification and tests.

+ Change management for public API
- Public API changes require updating all call sites in the same change set.
- Removing or renaming exports must be tool-verified as unused.

+ Build configuration uniformity
- One TS module resolution strategy across the repo.
- One lint config and one formatter config applied to all modules.

+ Module documentation convention
- Each module documents:
  - responsibility
  - allowed dependencies
  - what is internal vs public
- Documentation is descriptive. Tooling is authoritative.

+ Public API manifest
- Each module owns an api.ts or api.md listing its public exports and purpose.
- CI checks api manifest drift against index.ts exports.

+ Import layering rules
- internal code imports internal by relative path only within the module.
- public code imports internal through internal facades only, no cross-folder reach.

+ Strict type boundaries
- Public exports must not leak internal-only types.
- Exported types must be stable, documented, and versioned as contracts.

+ Runtime boundary rules
- Node-only code stays in a dedicated node module or node-only internal folder.
- Browser-only code stays in a dedicated web module or web-only internal folder.
- Cross-runtime code avoids direct global usage and uses adapters owned by the module.

+ Side effects policy
- Public modules must be side-effect free at import time.
- Side effects live behind explicit functions, with names that reveal behavior.

+ Error model uniformity
- Public APIs return typed results or throw typed errors, one repo-wide choice.
- Errors include stable codes, message, and cause, without leaking secrets.

+ Logging and observability
- Public APIs accept a logger or use a repo logger interface, no direct console usage.
- Logs carry event name, module, and stable fields.
- Hot paths avoid per-iteration logs.

+ Security boundaries
- Any input crossing a trust boundary is validated at the owning module edge.
- Validation rules live next to the public entrypoint, not scattered.
- Dangerous sinks require safe wrappers owned by a dedicated security module.

+ Secrets handling
- No secrets in source, tests, fixtures, or logs.
- Secrets flow through a typed config object, never environment lookups inside business code.

+ Configuration rules
- One config loading path.
- Config is immutable after boot.
- Config access goes through a dedicated config module, no direct process.env use outside it.

+ Feature flag rules
- Flags live in one module and expose typed accessors.
- Flags are named by user-facing behavior, not ticket IDs.
- Flags have expiry dates and removal tasks.
- Flags never gate module boundary rules.

+ Deprecation rules
- Deprecations use explicit deprecated exports with JSDoc and removal date.
- No compat alias exports in index.ts.
- Consumers migrate before removal in the same release train.

+ Versioning policy for public APIs
- Breaking export changes require a version bump in the repo policy.
- Non-breaking additions require tests and docs updates.

+ Dependency hygiene
- Each module declares third-party deps in one place and documents purpose.
- No transitive dependency reliance for public APIs.
- No dual competing libs for the same concern without an explicit decision record.

+ No hidden coupling
- Cross-module communication uses explicit types and functions, no shared mutable singletons.
- Shared state lives in one owner module with explicit lifecycle methods.

+ Concurrency and async rules
- Public async APIs accept AbortSignal where long work exists.
- No unbounded parallelism without explicit limits.
- No background work started on import.

+ Performance rules
- Hot paths avoid allocations in loops and avoid polymorphic shapes.
- Performance-sensitive APIs document complexity and constraints.
- Benchmarks exist for critical modules, run in CI on demand.

+ Lint rules for code health
- No unused exports.
- No implicit any.
- No floating promises.
- Exhaustive switch over discriminated unions.

+ Formatting and file hygiene
- One line ending and one charset policy.
- Consistent import ordering enforced by tooling.
- No generated artifacts committed unless explicitly required.

+ Build outputs and packaging
- Build output folders are ignored by default.
- Public package entrypoints map to module index.ts only.
- Tree-shaking friendliness is preserved, no re-export chains that block it.

+ Documentation minimums
- Each module has a short README with purpose, public API summary, and examples.

+ Tooling enforcement list
- Boundary lint rule set for deep imports and internal imports.
- Cycle detection for module graph.
- API surface diff check for index.ts exports.
- Naming checks for folders, files, symbols.

+ Repository layout invariants
- src/modules is the only module root.
- Non-module code lives outside src/modules and must not be imported by modules unless explicitly allowed.
