4. RANKING EXPLANATION (Reviewer point 5B)
═══════════════════════════════════════════════════════════════════════

Provider ranking formula:
  effective = max(0, baseScore + preferenceBoost + recentSuccessBoost
                               - healthPenalty - cachePenalty)

Tie-breaking order (getRankedProviders):
  1. Higher effective score
  2. Tool-confirmed providers preferred
  3. Higher selection count (incumbency — intentional policy)
  4. Alphabetical name (deterministic)

Incumbency bias via selections count IS intentional:
  - Providers with more successful completions get tie-break preference
  - This reduces risk — proven providers are preferred when scores tie
  - New providers can still win by earning a higher base score

5. ADAPTIVE CONTEXT EXPLANATION (Reviewer point 6)
═══════════════════════════════════════════════════════════════════════

Adaptive context sizing is IN-PROCESS EPHEMERAL:
  - 413/context errors → dynamicMaxTokens reduced in memory
  - Applies within same process and same fallback cascade
  - Resets on bridge restart (intentional — documented in provider-states.mjs)

Rationale for ephemeral:
  - Rate-limit windows are time-bound (60s)
  - Context caps vary by provider and change over time
  - Stale persisted caps could cause unnecessary truncation
  - No I/O cost on every request

For the showcase: describe as "in-process adaptive behavior" —
the system learns within a single cascade but does not persist
learned sizing across restarts.
