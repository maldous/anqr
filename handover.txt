## KNOWN REMAINING ISSUES

### 1. Issues cycling fast → Canceled (high priority)
**Symptom:** Worktrees complete issues in ~2 min, Linear shows Canceled not Done.
**Root cause:** Agents may still not produce file changes for some Sonar rules.
  - Some rules involve complex refactors (90 occurrences of Array#push) — agent
    may attempt changes but produce no git diff.
  - The file:line fix (commit 06349ed13) should help but wasn't deployed long enough
    to verify at handover.
**How to debug:**
  - Watch Linear for first "Done" issues
  - If still Canceled: check runner voice_speak Discord messages for "no file changes"
  - Check: reports/symphony/external-completions.log for cancellation reasons

### 2. validation_failed_repairable — AI breaks tests while fixing Sonar
**Symptom:** Agent renames catch parameter → breaks test assertion on that variable.
**Root cause:** Sonar rule S7718 (rename catch param to error_) — agent renames in
  production code AND test files, but test assertions check the old name.
**How to debug:**
  - Check finalization.lastError for "test-unit" failures
  - Look at the specific test file — usually active-job-ownership.spec.ts or similar
**Mitigation:** The repair loop (validation_failed_repairable) retries up to 3x.
  After that it moves to Backlog. Consider adding test guidance in WORKFLOW.md:
  "When renaming catch parameters, only rename in the catch block, not in test
   assertion strings."

### 3. Consolidated vs individual issue format
**Current:** One Linear issue per Sonar rule, e.g. "Sonar: javascript:S7778 (90)"
**Trade-off:** Consolidated saves Linear quota but gives the agent a big batch.
  Agent may fix 10/90 occurrences and get a successful commit, leaving 80 unfixed.
  The Sonar issue stays open until all occurrences are fixed.
**Alternative:** Individual issues per finding (old approach) — more Linear quota
  but each issue is a targeted 1-line fix with higher success rate.
**Status:** Current consolidated format with file:line is a compromise. Monitor
  whether agents fix all occurrences or partial.

### 4. changedFiles=[] in finalization → commit_failed_repairable loop
**Symptom:** Issue gets commit_failed_repairable with changedFiles=[] and headSha
  pointing to current main.
**Root cause:** Agent called str_replace but the target string wasn't found (already
  fixed or wrong line), so git sees nothing to commit.
**Impact:** Runner retries with "fix commit issues" prompt, agent re-runs, same result.
  Eventually hits max attempts and moves to Backlog.
**Fix needed:** When changedFiles=[] AND headSha=current main → cancel immediately
  rather than entering repair loop. The Sonar finding is already fixed.
  Location: execute-issue.mjs around line 1502 — add check before setting
  commit_failed_repairable state.

### 5. Integration layer uses symphony/integration branch on main checkout
**Issue:** The integrator runs from the main repo checkout (/home/user/src/anqr).
  When I (Claude) also commit to main from here, the integrator's push races with
  my manual commits. The retry fix (commit ed96419de) handles this, but it adds
  latency.
**Best practice:** Don't commit to main manually while the integrator is running.
  All code changes should go through worktree branches.

## PIPELINE ARCHITECTURE QUICK REFERENCE

```
Linear Todo issue
    ↓ scheduler (15s poll)
    → claims issue, dispatches to worktree (wt1-4)
    ↓ executor bridge (symphony-openai-bridge.mjs, port 4321-4328)
    → spawns runner subprocess (symphony-runner/runtime.mjs --issue ANQ-xxx)
    ↓ runner
    → acquires lease (20 min TTL, heartbeat every 30s)
    → sync worktree: git fetch + reset --hard origin/main
    → calls AI agent via bridge (model selection, tool provision)
    → agent makes file changes (str_replace, write_file tools)
    → validation: lint + test-unit + typecheck
    → git commit + push symphony/wt{n} branch
    → sets finalization: integration_pending
    ↓ integrator (30s poll)
    → cherry-picks wt branch commit onto origin/main
    → pushes HEAD:main (up to 3 retries on non-fast-forward)
    → calls publishEvidenceAndClose → Linear Done
    ↓ Linear Done ✓
```

### Failure states and recovery
| State | Cause | Recovery |
|-------|-------|----------|
| quarantined | 3x sync failures | recovery service: reset_to_main |
| validation_failed_repairable | lint/test fail | sticky repair (same wt) x3 |
| commit_failed_repairable | nothing to commit | sticky repair (re-runs agent) |
| integration_failed_repairable | cherry-pick conflict | sticky repair (agent resolves) |
| Backlog (Linear) | max retries exhausted | manual: move back to Todo |

- RUNNER_MAX_RETRIES = 10
- RUNNER_VALIDATION_REPAIR_MAX = 3
- RECOVERY_OWNERSHIP_CONFIDENCE_THRESHOLD = 0.7
- RECOVERY_QUARANTINE_THRESHOLD_MS = 600_000 (10 min)
- DEFAULT_LEASE_MS = 20 * 60 * 1000 (20 min)
- TARGET_MIN = queue target depth
