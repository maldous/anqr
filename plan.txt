# Work Item: Shared Session Context and Worktree-Safe Execution for Discord and Linear

## Summary

Follow-up requests can lose effective context because routing affinity and conversational state are handled in different places.

The Discord router keeps sticky session → worktree routing, but bridge-level session state, provider health, and credit-gate state are still effectively local to each bridge instance. There is also no durable Discord active-job ownership, and request attribution is not concurrency-safe.

This work item introduces:

- shared session context across worktrees
- durable active-job ownership for Discord
- shared provider metrics and health
- concurrency-safe request attribution
- explicit job/worktree validation for tool execution
- recovery rules for stale Discord jobs

## Problem Statement

Current failure modes:

1. A Discord follow-up can arrive at a different worktree and lose task context.
2. `currentRequestId` is module-global and unsafe under concurrency.
3. Discord has sticky routing but no durable active-job claim/lease model.
4. Session state is bridge-local rather than shared across worktrees.
5. Provider health and credit-gate state are not consistently shared.
6. Tool execution is not explicitly bound to job/worktree ownership.
7. Router “least loaded” selection is based on local counters, not durable active-job ownership.

---

## Objective

Create a shared, model-agnostic context and ownership model that:

- preserves per-session and per-job context across worktrees
- allows model changes without replaying full raw history
- keeps provider metrics globally shared
- isolates unrelated jobs from each other
- binds tool execution to the correct job and worktree
- prevents active Discord jobs from drifting between worktrees
- supports recovery when a Discord worktree dies mid-task

## Acceptance Criteria

1. A Discord follow-up retains usable task context across worktree and process boundaries.
2. An active Discord session stays pinned to one assigned worktree until completion or recovery.
3. Provider health and credit-gate state are shared across worktrees.
4. Model switching does not require replay of full raw task history.
5. Session context is isolated per conversation or issue, not global across Discord.
6. Concurrent requests do not corrupt request attribution.
7. Mutating tools validate job/worktree ownership before execution.
8. Stale Discord jobs are recoverable with explicit reassignment and rehydration.
9. Unrelated active jobs do not receive each other’s context.

---

## Risks and Gotchas

- Do not point multiple processes at one shared monolithic JSON file without locking.
- Do not key long-lived context only by `x-openclaw-session`.
- Do not store unbounded raw tool output in prompt context.
- Do not silently move active Discord tasks between worktrees.
- Do not mix global provider metrics with per-job context.
- Do not assume router-local active request counters represent durable load.
- Do not fix only the bridge tool path and miss symphony-agent tool execution.

---

## Priority

High

## Definition of Done

The system preserves per-task context across worktrees and model changes without sharing unrelated in-flight job state, and mutating work remains bound to the correct job and worktree under concurrency, restart, and recovery conditions.
