Implementation report and remediation brief

1. Executive summary

This pass should harden the harness around six production blockers:

1. make control-plane state truly restart-safe and concurrency-safe
2. make Discord/OpenClaw session and thread continuity actually work
3. carry correlation and evidence end to end, not just at ingress
4. make Linear webhook verification fail closed in production
5. make provider routing follow actual ranking and constraints, without hidden Codex or Codebuff preference
6. clean the user-facing Discord path so it stops exposing internal metadata and provider fallback noise

What matters most:
- fix real runtime correctness first
- remove deployment and startup ambiguity
- tighten provider routing semantics
- finish the partial remediation surfaces so they are actually used
- leave the touched areas statically clean

2. Feedback-to-fix mapping

A. Durable state and restart safety

Finding
- feedback-1 and feedback-2 both identify restart-unsound state.
- confirmed in code:
  - harness/ops/integrations/model/linear-webhook-receiver/runtime.mjs still clears recentDeliveries and activeIssues on startup
  - harness/ops/lib/durable-kv.mjs is file-backed but not safe for concurrent multi-process read-modify-write

What is actually wrong
- “durable” state is being wiped on startup in the webhook receiver
- the new durable-kv layer is not lock-safe, so queue and dedupe correctness are not guaranteed under concurrent writers

Root cause
- remediation introduced file-backed persistence without integrating it with the existing locked state plane in harness/ops/core/symphony-state/*
- webhook runtime still contains legacy “clear stale state on startup” behavior

Required changes
1. remove startup clearing from:
   - harness/ops/integrations/model/linear-webhook-receiver/runtime.mjs
2. move durable control state behind a locked state backend
   - either replace harness/ops/lib/durable-kv.mjs with a lock-aware implementation
   - or reimplement recent-deliveries, active-issues, session routing, and linear queue using harness/ops/core/symphony-state/*
3. add expiry-aware records instead of blanket clear
   - dedupe entries should expire by timestamp
   - active issue leases should expire by lease age or explicit completion
4. add atomic update helpers for:
   - durable set add-if-absent
   - durable queue enqueue/dequeue
   - durable map compare-and-set where needed

Primary files
- harness/ops/integrations/model/linear-webhook-receiver/runtime.mjs
- harness/ops/integrations/model/linear-webhook-receiver/recent-deliveries.mjs
- harness/ops/integrations/model/linear-webhook-receiver/active-issues.mjs
- harness/ops/integrations/model/symphony-agent-router/linear-queue.mjs
- harness/ops/lib/durable-kv.mjs
- harness/ops/core/symphony-state/*

Expected behavior after fix
- restart does not wipe dedupe or active issue state
- concurrent webhook or router activity does not corrupt queue or dedupe files
- state expires naturally, not by service restart

Verification
- restart linear webhook during active webhook delivery and confirm no duplicate execution
- run concurrent enqueue/dequeue tests and verify queue integrity
- run stress test with repeated webhook deliveries and confirm dedupe survives restarts

B. Discord/OpenClaw session and thread continuity

Finding
- feedback-1 and feedback-2 both identify broken session continuity and thread handling
- confirmed in code:
  - discord-request-router/server.mjs accepts x-openclaw-session and x-openclaw-session-key
  - discord-request-router/process-and-proxy.mjs only reads x-openclaw-session
  - symphony-openai-bridge/server.mjs only reads x-openclaw-session
  - session-thread-names.mjs and discord-thread-cache.mjs are in-memory only

What is actually wrong
- the session identity contract is inconsistent across ingress, router, and executor
- thread mapping is in-memory only and is lost on restart
- user-visible thread names are derived from bad metadata

Root cause
- remediation added partial session support but did not standardize the session header contract end to end
- sticky session-to-worktree and session-to-thread mappings were not moved into durable state

Required changes
1. standardize one session identity contract everywhere
   - support both x-openclaw-session and x-openclaw-session-key at the edge if needed
   - normalize them immediately into one canonical internal key
   - pass only the canonical form downstream
2. persist sticky session routing and thread mapping durably
   - replace:
     - harness/ops/integrations/model/discord-request-router/session-thread-names.mjs
     - harness/ops/integrations/notifications/openclaw-discord/discord-thread-cache.mjs
   - with durable, lock-safe state
3. ensure worktree selection uses the same durable session key
4. ensure executor bridge uses the same canonical session key for provider/session stickiness
5. clean thread naming
   - never derive thread names from “Sender (untrusted metadata)” or raw transcript wrappers
   - generate short stable thread titles from the first meaningful user message only

D. Linear webhook security

Finding
- feedback-1 identifies permissive signature verification
- confirmed in code:
  - verify-signature.mjs returns true when signature missing
  - verify-signature.mjs returns true when WEBHOOK_SECRET missing
  - webhook-secret.mjs falls back to LINEAR_API_KEY

What is actually wrong
- production webhook verification is effectively optional

Root cause
- test-mode shortcuts were left active in the main verification path

E. Provider selection, ranking, and hidden preference removal

Finding
- feedback requires ranked provider selection with no hidden Codex-first or Codebuff-second behavior
- current code already has separate codebuff-paid and codebuff-free providers
- user clarification: Codebuff uses one API key, but the SDK supports paid and free mode and both should be ranked separately

Confirmed in code
- build-static-providers.mjs already defines:
  - codebuff-paid
  - codebuff-free
- both use CODEBUFF_API_KEY but different costMode/sessionMode
- select-provider.mjs currently score-boost merges preferred and fallback candidates
- build-selection-options.mjs injects preferredNames heavily

What is actually wrong
- ranking can still be distorted by preferred-name score boosting
- paid providers can float above actual ranking in ways that are not explicit enough
- Codebuff paid/free separation exists, but needs strict runtime independence in ranking, probing, and fallback

Root cause
- provider ranking and provider preference are mixed together

Required changes
1. make ranked order the default truth
   - selectProvider should iterate ranked candidates in ranked order
   - do not interleave preferredNames 1:1 unless route explicitly requests a pinned/preferred subset
2. use preferredNames only for:
   - explicit route constraints
   - sticky session reuse of a still-healthy provider
   - evaluation sampling if deliberately enabled
3. keep codebuff-paid and codebuff-free as separate providers with the same credential
4. ensure all metrics, health, probe results, cooldowns, and selection counts are tracked independently for:
   - codebuff-paid
   - codebuff-free
5. ensure invokeWithFallback and invokeWithFallbackStream never collapse codebuff modes into one implicit provider
6. ensure getSharedClient caching remains mode-aware and cwd-aware
7. ensure probe and selection logs clearly distinguish codebuff-paid from codebuff-free
8. ensure Codex is just another ranked paid provider, not an implicit first choice

F. Startup probing, capability classification, and catalog hygiene

Finding
- feedback calls out noisy startup probing, predictable invalid capability checks, and repeated rediscovery of known incompatibilities
- current code already tracks toolCapableProviders and nonToolCapableProviders, but startup remains noisy and expensive

What is actually wrong
- startup probing is broader than it needs to be
- known incompatible providers/models are still rediscovered through repeated probe attempts
- local services can be marked degraded during normal startup sequencing

Root cause
- provider capability and readiness classification are not cleanly split into:
  - configured
  - reachable
  - tool-capable
  - temporarily unavailable
  - permanently incompatible

Required changes
1. pre-filter known incompatible or non-tool-capable provider classes earlier
2. add permanent or long-lived negative classification for:
   - providers that are structurally non-tool-capable
   - providers/models known to emit invalid raw tool JSON in this harness mode
3. separate startup warmup from failure accounting
   - local services like Context7 should not count as degraded during their expected boot window
4. reduce probe volume by:
   - not probing providers lacking required env vars
   - not probing permanently blocked model classes
   - caching capability class more strongly
5. keep provider health transitions accurate
   - startup not-ready is not the same as runtime degraded

3. Key implementation decisions

Decision 1
Treat Codebuff as two separate providers sharing one API key:
- codebuff-paid
- codebuff-free
Do not create a fake second credential model.
Do keep separate ranking, probing, health, cooldown, metrics, and session stickiness for each mode.

Decision 2
Do not preserve the current score-boost merge in select-provider unless a route explicitly asks for preference.
Ranked order should be the default truth.

Decision 3
Do not keep durable-kv as an unlocked JSON store for critical control-plane semantics.
Either move it under the existing symphony-state locking model or add equivalent locking.

Decision 4
Make one canonical session key end to end.
Do not keep parallel x-openclaw-session versus x-openclaw-session-key semantics beyond the first ingress normalization point.

Decision 5
Task evidence must become the authoritative lifecycle record, or the unused lifecycle API should be removed.
Do not leave it half-integrated.

Decision 6
Do not surface non-terminal provider fallback failures in the user-facing Discord path.
Keep them in operator logs.

Decision 7
Fail closed for webhook security and critical startup configuration in production.
Do not let test shortcuts leak into production runtime.
