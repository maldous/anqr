## 1. Executive Verdict

The harness is **partially delivered**. This refreshed source tree is materially better than the last pass. Several previously critical issues are now genuinely fixed in code, including fail-closed Linear webhook verification, removal of webhook startup clearing, more complete correlation and task-evidence wiring, durable session/thread maps, ranked provider selection without the old hidden preference pattern, and broader watchdog coverage. The overall approach remains **sound but overcomplicated**. The methodology is **viable**, but the platform is still not production-ready because there are still hard blockers in security, startup contracts, operational truth, OpenClaw configuration, documentation drift, and a few remaining concurrency and observability gaps. The team should **stabilize and simplify**, not expand.

## 3. Real Architecture Summary

The actual implemented architecture is a **multi-service control plane plus worktree execution plane**.

The **control plane** is:

* `anqr-linear-webhook.service` on `18791`
* `anqr-discord-router.service` on `18790`
* `anqr-symphony-router.service` on `4319`
* `anqr-symphony-integrator.service`
* `anqr-symphony-worktree-recovery.service`
* `anqr-watchdog.service`
* `openclaw-gateway.service` on `18789`
* support surfaces like `anqr-context7-mcp.service`, `litellm-proxy.service`, and `model-injector-proxy.service`

The **execution plane** is:

* `anqr-symphony-executor@1..8.service`
* worktree-local execution via `harness/ops/integrations/model/symphony-openai-bridge.mjs`
* `wt1-wt4` reserved for Linear
* `wt5-wt8` reserved for Discord

The **real critical coupling points** are:

* `harness/ops/lib/durable-kv.mjs`
* `harness/ops/core/task-evidence.mjs`
* `harness/ops/core/symphony-state/*`
* `harness/ops/integrations/model/symphony-agent-router/*`
* `harness/ops/integrations/model/symphony-openai-bridge/server.mjs`
* `harness/ops/orchestration/symphony-runner/execute-issue.mjs`
* `harness/ops/orchestration/symphony-integrator/integrate-candidate.mjs`
* `harness/ops/runtime/openclaw-config/openclaw.json`

This is still **not a clean hexagonal runtime**. It is a deliberate orchestration system with some adapter isolation, but the runtime still couples routing, provider selection, worktree mutation, notifications, and integration behavior more tightly than the doctrine claims.

## 4. End-to-End Flow Assessment

### Discord/OpenClaw to router to executor

**Intended flow**
OpenClaw should forward Discord requests into the Discord router, the router should preserve session and thread context, route to `wt5-wt8`, and keep follow-up turns on the same worktree and same thread.

**Actual implemented flow**
`openclaw-gateway.service` fronts the Discord path. `harness/ops/integrations/model/discord-request-router/server.mjs` accepts both `x-openclaw-session` and `x-openclaw-session-key`, chooses a worktree via `getLeastLoadedWorktree(sessionId)`, and `process-and-proxy.mjs` forwards the request to the executor bridge. Session-to-thread and thread cache state are now durable maps instead of in-memory maps. The executor bridge also accepts both session headers.

**Verified files/services**
`services/systemd/openclaw-gateway.service`
`services/systemd/anqr-discord-router.service`
`harness/ops/integrations/model/discord-request-router/server.mjs`
`harness/ops/integrations/model/discord-request-router/process-and-proxy.mjs`
`harness/ops/integrations/model/discord-request-router/session-thread-names.mjs`
`harness/ops/integrations/notifications/openclaw-discord/discord-thread-cache.mjs`
`harness/ops/integrations/model/symphony-openai-bridge/server.mjs`

**Failure points**

* session continuity is improved in code but still not proven operationally against the current OpenClaw deployment behavior
* OpenClaw config still allows request-supplied session keys
* user-path cleanliness still depends on OpenClaw plus Discord path behavior, not just harness-side sanitization

**Verdict**
**Partially delivered.**

## 5. Major Findings

### Critical

**2. OpenClaw hook/session model remains too permissive for a production control boundary**
Severity: Critical
Why it matters: Arbitrary request-supplied session identity is still allowed, which undermines routing trust and session integrity.
Exact evidence: `harness/ops/runtime/openclaw-config/openclaw.json` sets `hooks.allowRequestSessionKey` to `true`. The debug bundle shows the same in `harness-openclaw-debug/config/openclaw.json`.
Problem type: Proven
Recommended fix: Disable arbitrary request session-key override, or strictly restrict it with explicit prefixes and a default session-key strategy.

**3. Queue and dedupe state remain unsafe under lock exhaustion**
Severity: Critical
Why it matters: The platform now has locking, but it can still drop back to unlocked state mutation under contention. That is not safe for control-plane correctness.
Exact evidence: `harness/ops/lib/durable-kv.mjs` acquires per-store lock files, but after `LOCK_MAX_ATTEMPTS` it logs a warning and proceeds unlocked with `return fn();`.
Problem type: Proven
Recommended fix: Never proceed unlocked for queue/dedupe mutation. Move this state into the locked `harness/ops/core/symphony-state/*` plane or make lock acquisition failure a hard failure.

### High

**4. Root and harness doctrine still materially misdescribe the runtime**
Severity: High
Why it matters: Operators still have two truths: the code and the docs.
Exact evidence:

* `README.md` still claims “90+ E2E tests” and “fully operational” language
* `AGENTS.md` still describes pre-request sync and post-completion push directly to `origin/main` by each worktree
* `docs/harness/12-concurrent-execution-with-worktrees.md` still contains stale runner-era and direct-push guidance
* `services/systemd/anqr-symphony-router.service` still says `Linear → Linear Runner → Symphony Router`
* `services/systemd/anqr-watchdog.service` still says it rolls back to a previous git commit
  Problem type: Proven
  Recommended fix: Rewrite root docs and stale harness docs from active code and service truth only. Fix misleading service comments immediately.

**5. Critical services still tolerate missing env files silently**
Severity: High
Why it matters: Startup success can still mean “running partially configured”.
Exact evidence: `services/systemd/anqr-linear-webhook.service`, `anqr-discord-router.service`, `anqr-symphony-router.service`, `anqr-symphony-executor@.service`, `anqr-watchdog.service`, and many related units use `EnvironmentFile=-...`, making env files optional.
Problem type: Proven
Recommended fix: Make required env files mandatory for critical services or add explicit in-process startup validation that exits non-zero when required config is missing.

**6. OpenClaw still appears to have a runtime port/control-surface ambiguity with the harness**
Severity: High
Why it matters: The debug bundle still shows OpenClaw browser control listening on `127.0.0.1:18791`, while the harness Linear webhook is also configured for `18791`.
Exact evidence:

* `services/systemd/anqr-linear-webhook.service` sets `LINEAR_WEBHOOK_PORT=18791`
* `harness-openclaw-debug/journal/openclaw-gateway.service.journal.txt` repeatedly logs browser control on `http://127.0.0.1:18791/`
  Problem type: Proven in runtime bundle, root cause partly inferred
  Recommended fix: Make OpenClaw browser control port explicit and non-overlapping, then verify with live listeners.

**7. Direct push to `origin/main` remains the integration model**
Severity: High
Why it matters: A single automation error can still land directly on main.
Exact evidence: `harness/ops/orchestration/symphony-integrator/integrate-candidate.mjs` runs `git("push", "origin", "HEAD:main")`.
Problem type: Proven
Recommended fix: Move to a protected integration branch or merge queue unless there is a strong, explicitly accepted reason not to.

### Medium

**8. Reporting and evidence are improved, but not yet complete enough for a clean production audit trail**
Severity: Medium
Why it matters: The evidence model is now real, but still not comprehensive across watchdog/recovery and every user path.
Exact evidence: `task-evidence.mjs` now has runtime consumers in `discord-request-router/process-and-proxy.mjs`, `symphony-openai-bridge/server.mjs`, `symphony-runner/execute-issue.mjs`, and `symphony-integrator/integrate-candidate.mjs`, but watchdog/recovery are not joined into the same lifecycle record.
Problem type: Proven
Recommended fix: Finish evidence integration for watchdog and worktree recovery, and add a one-command task reconstruction tool.

**9. The live E2E suite is useful, but still not a full end-to-end proof of production behavior**
Severity: Medium
Why it matters: Current E2E tests prove live ingress and some routing, but not a full mutation-to-integration lifecycle.
Exact evidence: `tests/e2e/linear-flow.spec.ts`, `tests/e2e/discord-flow.spec.ts`, and `tests/e2e/integration-promotion.spec.ts` are real live-service tests, but they do not prove one full task from ingress through validation, push, and final integration to main. The spec headers also reference `vitest.e2e.config.ts`, which is not present.
Problem type: Proven
Recommended fix: Add a hermetic full-path 2E suite and expose it in `package.json`.

**10. OpenClaw source config still exposes an overly broad tool surface**
Severity: Medium
Why it matters: The control surface is broader than necessary for a production conversational gateway.
Exact evidence: `harness/ops/runtime/openclaw-config/openclaw.json` allows `shell`, `run_terminal_command`, `write_file`, `str_replace`, `run_file_change_hooks`, and broad tool/plugin combinations at the gateway layer.
Problem type: Proven
Recommended fix: Minimize gateway-exposed tools and reserve high-risk mutation tools for the harness execution plane only.

### Low

**11. The previous deployment-drift issue for the OpenClaw unit appears resolved**
Severity: Low
Why it matters: This is an improvement worth recording.
Exact evidence: `services/systemd/openclaw-gateway.service` now matches `harness-openclaw-debug/systemd/openclaw-gateway.service.unit.txt` in the debug bundle.
Problem type: Proven resolved
Recommended fix: None for the unit itself. Keep the source/runtime reconciliation discipline.

## 6. Architecture Assessment

**Hexagonal integrity**
Improved, but still partial. The platform has clearer adapter boundaries than before, but runtime coordination still crosses too many layers.

**Contract enforcement**
Better than the previous pass. The code now reflects several critical contract corrections, especially for webhook verification, durable session maps, and ranked provider selection. The docs still weaken trust.

**Adapter boundaries**
OpenClaw, Discord, provider routing, and worktree execution are still too entangled, especially through `harness/ops/integrations/model/symphony-openai-bridge/server.mjs`.

**Orchestration design**
Still capable but over-layered. Router, bridge, runner, integrator, recovery, watchdog, and a custom file-backed state plane create more complexity than a production baseline should carry.

**Service decomposition**
Reasonable. Ingress, execution, integration, and support services are separated in sensible ways. The remaining problems are overlap, startup permissiveness, and drift.

**Worktree strategy**
Still good. `wt1-wt4` and `wt5-wt8` remain a sensible split. The worktree model is one of the stronger design choices in the platform.

**Systemd strategy**
Acceptable, but not yet production-hard. The units are better than before, but many still allow partial startup, and comments remain stale.

**AI orchestration methodology**
Viable. Ranked provider selection is better and Codebuff paid/free handling is now structurally cleaner. The runtime still needs simplification and harder operational boundaries.

**Operational simplicity versus accidental complexity**
Still too much accidental complexity. The platform is improving, but it is still doing too much through bespoke orchestration instead of boring, explicit contracts.

## 7. Logging and Observability Assessment

**What is good**

* correlation IDs are now real and used more widely
* ingress evidence is real for Discord and Linear
* routing, provider, execution, validation, push, and integration evidence are partially wired
* Context7 startup logging now distinguishes warming from failure
* watchdog coverage now includes executors

**What is missing**

* full watchdog/recovery evidence integration
* one authoritative per-task audit story that spans OpenClaw, router, executor, runner, and integrator
* explicit startup validation logs for missing required config
* clear separation of user-facing versus operator-facing provider fallback messages across the whole path

**What is dangerously missing**

* confidence that queue state remains correct under sustained concurrency
* a fully proven task reconstruction path from Discord user turn to integration result

**Whether incident reconstruction is realistically possible**
Better than before, but still only partial. For many tasks, an operator could reconstruct ingress, routing, and some execution steps. Full clean reconstruction across OpenClaw plus harness still is not guaranteed.

**Required logging improvements**

1. Add startup validation logging to every critical service that depends on secrets or routing config.
2. Emit watchdog and recovery events into the same evidence model.
3. Log explicit canonical session identity and thread identity once per Discord request.
4. Distinguish user-path sanitization from operator-path debug logging more cleanly.
5. Add queue mutation logs that include lock outcomes, not just queue length.

**Required evidence/reporting improvements**

1. Finish wiring watchdog and recovery into `harness/ops/core/task-evidence.mjs`.
2. Add one operator tool that reconstructs a task by correlation ID.
3. Record OpenClaw session and thread linkage durably.
4. Prove one full Discord and one full Linear lifecycle in a production-like E2E path.

## 12. Go / No-Go Recommendation

**Is the harness ready to be treated as operational?**
**No-Go** for a production-ready autonomous platform.

**Should the team continue investing in it in its current form?**
No. Continue only as a hardening and simplification effort, not as a feature-growth effort.

**Should the architecture be simplified?**
Yes. Keep the worktree split, ingress services, ranked provider routing, and integrator. Reduce bespoke state handling, tighten OpenClaw, and make startup and evidence contracts stricter.

**Minimum set of fixes required before the team can safely return focus to the main project**

2. harden OpenClaw session and tool exposure
3. make queue/dedupe state safe under contention without unlocked fallback
4. make critical startup config fail closed
5. resolve the OpenClaw/Linear webhook port ambiguity
6. purge stale doctrine and service comments
7. prove one full Discord and one full Linear lifecycle end to end
