You are a principal platform engineer, SRE, and staff-level software architect.

Your task is to fully implement the remediation plan for the ANQR harness based on the engineering verdict below.

Goal:
Make the harness operationally reliable, auditable, and simple enough that the team can stop spending most of its time on harness maintenance.

Operating rules:
1. Work from code and service files as truth.
2. Do not preserve broken legacy behavior for compatibility unless it is explicitly still required by the active runtime.
3. Prefer simplification over feature expansion.
4. Do not add more orchestration layers.
5. Every change must improve one or more of:
   - correctness
   - safety
   - observability
   - durability
   - testability
   - operational simplicity
6. Preserve the current main capabilities unless the task explicitly says to remove or replace them:
   - Discord/OpenClaw ingress
   - Linear ingress
   - worktree-based execution
   - provider routing
   - integration back to the repo
7. Treat docs, Structurizr, and README claims as untrusted until verified against code.
8. Update documentation only after code and service truth are established.
9. Do not stop at analysis. Implement the fixes.
10. Return full file changes.

Required output:
- Full file implementations
- Updated systemd units
- Updated tests
- Updated runtime docs
- Updated Structurizr workspace files if runtime truth changes
- A final implementation report that maps each completed item to files changed and validation evidence

Implementation order:
Follow the phases below in order.

======================================================================
PHASE 0. IMMEDIATE CONTAINMENT
======================================================================

Task P0-1. Remove secrets from committed unit files
Objective:
Eliminate inline secrets from systemd units and move them to env-file based loading.

Primary files:
- services/systemd/openclaw-gateway.service
- any other service unit containing Environment= secrets
- any supporting startup scripts that assume inline secrets

Required changes:
- Replace inline secret values with EnvironmentFile= or equivalent secure loading
- Standardize secret variable names
- Add clear failure behavior if env files are missing
- Do not leave fallback hardcoded secrets in repo files

Acceptance criteria:
- No committed service file contains live secrets
- Services fail clearly if required secrets are absent
- Secret loading is documented in runtime docs

Validation:
- grep for known secret-bearing Environment= lines in services/
- dry-run service inspection shows env-file based loading only

Task P0-2. Disable unsafe watchdog rollback behavior
Objective:
Stop automated git hard-reset rollback from watchdog logic.

Primary files:
- harness/ops/runtime/watchdog/bridge-watchdog/rollback-and-restart.mjs
- harness/ops/runtime/watchdog/bridge-watchdog/*
- services/systemd/anqr-watchdog.service

Required changes:
- Remove or disable automatic git rollback
- Restrict watchdog behavior to restart, quarantine, report, and alert
- Record explicit evidence when watchdog intervenes

Acceptance criteria:
- Watchdog never performs git reset --hard automatically
- Watchdog interventions are logged with structured evidence

Validation:
- Simulated failing health check causes safe restart/report behavior only

Task P0-3. Make readiness checks truthful
Objective:
Ensure readiness checks fail when required runtime services are missing or inactive.

Primary files:
- harness/ops/harness-doctor/check-systemd-services.mjs
- any readiness wrappers or CLI entrypoints

Required changes:
- Split developer convenience checks from runtime readiness checks
- Required services must produce a failing result when not active
- Output must identify exactly which services are missing or inactive

Acceptance criteria:
- Production readiness cannot return green when critical services are down
- Output is explicit and machine-readable where possible

Validation:
- Stop a required unit and confirm readiness fails

PHASE 1. TRACEABILITY AND DURABLE CONTROL PLANE
======================================================================

Task P1-1. Introduce end-to-end correlation IDs
Objective:
Provide a single correlation ID from ingress through execution, provider routing, integration, and reporting.

Primary files:
- harness/ops/integrations/model/discord-request-router/*
- harness/ops/integrations/model/linear-webhook-receiver/*
- harness/ops/integrations/model/symphony-agent-router/*
- harness/ops/integrations/model/symphony-openai-bridge/*
- harness/ops/orchestration/symphony-runner/*
- harness/ops/orchestration/symphony-integrator/*
- harness/ops/integrations/notifications/openclaw-discord/*
- harness/ops/lib/logger/*

Required changes:
- Generate correlation ID at ingress
- Propagate it through HTTP headers, internal request objects, subprocess invocation, state transitions, logs, and evidence records
- Standardize log fields:
  - correlationId
  - service
  - worktreeId
  - issueIdentifier or requestIdentifier
  - providerName
  - route
  - attempt
  - stateTransition

Acceptance criteria:
- A single Discord request can be reconstructed end to end by correlation ID
- A single Linear issue execution can be reconstructed end to end by correlation ID

Validation:
- Add integration tests and sample evidence output for both flows

Task P1-2. Replace in-memory dedupe and queue control with durable state
Objective:
Move critical control-plane state out of process memory.

Primary files:
- harness/ops/integrations/model/linear-webhook-receiver/active-issues.mjs
- harness/ops/integrations/model/linear-webhook-receiver/recent-deliveries.mjs
- harness/ops/integrations/model/symphony-agent-router/linear-queue.mjs
- harness/ops/integrations/model/discord-request-router/session-thread-names.mjs
- harness/ops/core/symphony-state/*
- any queue-control modules under harness/ops/orchestration/symphony-queue-control/*

Required changes:
- Replace Set, Map, and array based transient control state with durable shared state or a clearly defined local datastore
- Persist:
  - recent webhook deliveries
  - active issue leases
  - queued issue records
  - session-to-worktree sticky routing
  - dispatch attempts
- Ensure restart-safe behavior

Acceptance criteria:
- Service restart does not lose dedupe correctness
- Service restart does not lose queue correctness
- Sticky routing survives router restart where required

Validation:
- Restart router/webhook services during synthetic traffic and verify no duplicate or dropped work

Task P1-3. Create authoritative task evidence records
Objective:
Make one durable evidence record per task or request.

Primary files:
- harness/ops/core/symphony-state/*
- harness/ops/orchestration/symphony-runner/*
- harness/ops/orchestration/symphony-integrator/*
- harness/ops/harness-report.mjs
- related reporting modules

Required changes:
- Persist one authoritative record per task/request
- Include:
  - ingress metadata
  - routing decision
  - worktree selection
  - provider selection and fallback events
  - execution start/end
  - validation result
  - push result
  - integration result
  - watchdog or recovery interference
- Make reports consume this source of truth

Acceptance criteria:
- One task can be audited without stitching together multiple unrelated logs by hand

Validation:
- Produce sample evidence output for one Discord task and one Linear task
