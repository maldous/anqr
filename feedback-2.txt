OpenClaw debug bundle review

Executive verdict

The OpenClaw debug bundle makes the runtime picture clearer. The platform is running real traffic, but it is still not a finished operational system. The bundle proves deployment drift, active security and control-plane weaknesses, poor Discord session continuity, noisy provider behavior in the user path, and at least one likely port/config collision between OpenClaw and the harness. This is still a stabilization platform, not a finished platform.

What this bundle materially changes

1. It confirms the live deployment does not fully match the remediated source tree.
2. It confirms OpenClaw itself is part of the operational problem, not only the harness routers and executors.
3. It shows the user-facing Discord path is affected by gateway restarts, stale-socket recovery, permissive session routing, and overly broad tool/security settings.
4. It adds new critical findings around live secret handling, gateway/runtime drift, and an apparent port collision.

Critical findings

1. Live deployment drift is real and severe.

The committed source service file has been remediated to use env files:
- services/systemd/openclaw-gateway.service
  - uses EnvironmentFile=%h/.config/systemd/user/anqr-ops.env
  - no inline secrets in the committed source copy

The live deployed unit captured in the debug bundle is different:
- harness-openclaw-debug/systemd/openclaw-gateway.service.unit.txt
  - still contains inline OPENROUTER_API_KEY
  - still contains inline ELEVENLABS_API_KEY
  - still hardcodes HOME=/home/user

This means the remediation has not been cleanly deployed to the running system. Source truth and runtime truth are diverged.

Operational implication:
Do not accept any claim of delivery based only on the source tree while the live deployed unit remains on the old secret-bearing version.

2. Live runtime secrets are still stored inline in OpenClaw config.

The debug bundle includes inline secrets in runtime config:
- harness-openclaw-debug/config/openclaw.json
  - env.OPENROUTER_API_KEY
  - env.ELEVENLABS_API_KEY
  - channels.discord.token
  - gateway.auth.token
  - hooks.token

This is not only a repo hygiene issue. It is a runtime security model issue. The OpenClaw configuration is acting as a secret store with high-impact credentials embedded directly in the config payload.

Operational implication:
Secret removal from committed unit files is not enough. The actual runtime still centralizes sensitive tokens in a live JSON config. The secrets need rotation and the runtime secret model needs redesign.

3. OpenClaw and the harness appear to claim the same port 18791.

The harness Linear webhook unit states:
- harness-openclaw-debug/systemd/anqr-linear-webhook.service.unit.txt
  - LINEAR_WEBHOOK_PORT=18791
  - URL: http://127.0.0.1:18791/linear/webhook

The OpenClaw gateway logs repeatedly state:
- harness-openclaw-debug/journal/openclaw-gateway.service.journal.txt
  - Browser control listening on http://127.0.0.1:18791/ (auth=token)

The harness webhook journal also states:
- harness-openclaw-debug/journal/anqr-linear-webhook.service.journal.txt
  - Listening: http://127.0.0.1:18791

Those claims are inconsistent on a single host and loopback interface. The later ss snapshot does not show either listener because the services were stopped by the time the snapshot was taken, so the bundle does not conclusively prove simultaneous bind success. But it does prove that two different runtime surfaces are configured to claim the same address and port.

Operational implication:
This is at minimum a configuration collision and at worst a hidden source of intermittent routing failure, misdirected health checks, or non-deterministic startup order behavior. It must be resolved before calling the platform operational.

4. OpenClaw itself reports that the gateway service config is out of date or non-standard.

The doctor output states:
- harness-openclaw-debug/cli/doctor.txt
  - Service config looks out of date or non-standard.
  - Gateway service entrypoint does not match the current install.
  - Gateway service PATH includes version managers or package managers; recommend a minimal PATH.
  - Recommendation: run a single gateway per machine for most setups.

The gateway status output states:
- harness-openclaw-debug/cli/gateway-status.txt
  - Other gateway-like services detected: anqr-discord-router.service
  - Recommendation: run a single gateway per machine for most setups.

Operational implication:
The gateway layer itself is flagging deployment drift and topology confusion. That is direct evidence that the current operational model is not cleanly converged.

5. Discord health is unstable at the gateway layer.

The OpenClaw gateway journal repeatedly shows:
- harness-openclaw-debug/journal/openclaw-gateway.service.journal.txt
  - health-monitor: restarting (reason: stale-socket)
  - gateway reconnect scheduled ...

These are not isolated events. They recur across the captured history.

Operational implication:
Even before the request reaches the harness Discord router, the Discord provider layer is already unstable enough to require recurring gateway health restarts. That reduces confidence in any claim of clean thread continuity or reliable real-time interaction.

6. The gateway is exposing a high-risk tool and trust model.

The OpenClaw security audit in:
- harness-openclaw-debug/logs/openclaw-2026-04-12.log
reports:
- CRITICAL: small models require sandboxing and web tools disabled
- gateway.tools.allow includes shell, which re-enables dangerous tools over HTTP
- hooks.defaultSessionKey is unset
- hooks.allowRequestSessionKey=true
- hooks.allowedSessionKeyPrefixes is unset or empty
- hooks.allowedAgentIds is unrestricted
- personal-assistant trust model warning for a potentially multi-user setup
- browser control enabled
- gateway HTTP session-key override enabled

The live config confirms several of those settings:
- harness-openclaw-debug/config/openclaw.json
  - gateway.tools.allow includes shell and file mutation tools
  - hooks.allowRequestSessionKey is true
  - hooks.token is short and static
  - no visible hook session-key prefix restriction
  - channels.discord is enabled with voice and broad runtime behavior

Operational implication:
The gateway is currently too permissive for a shared or semi-shared automation boundary. This is not a finished platform security posture.

High findings

7. The Discord path still lacks a clean session story.

The gateway audit explicitly notes:
- gateway.http.session_key_override_enabled
- hooks.request_session_key_enabled
- hooks.request_session_key_prefixes_missing
- hooks.default_session_key_unset

This aligns with the previously observed harness-side behavior where requests were repeatedly handled with session=(none) and worktree routing fell back to round-robin.

Operational implication:
The OpenClaw and harness session models are not yet converged into one safe, durable, operator-understandable path. That explains the observed missing thread continuity.

8. OpenClaw is logging broad tool allowlist mismatches.

The gateway logs repeatedly warn:
- tools.profile allowlist contains unknown entries
- agents.main.tools.allow allowlist contains unknown entries
- tools.allow allowlist contains unknown entries

Files:
- harness-openclaw-debug/logs/openclaw-2026-04-12.log
- harness-openclaw-debug/journal/openclaw-gateway.service.journal.txt

Operational implication:
The declared tool surface and the actual enabled tool/runtime surface are not cleanly aligned. That weakens trust in the configured execution model and makes incident analysis harder.

9. The gateway was not running at capture completion.

Both doctor and gateway-status report the gateway stopped:
- harness-openclaw-debug/cli/doctor.txt
- harness-openclaw-debug/cli/gateway-status.txt

The systemd status file shows:
- harness-openclaw-debug/systemd/openclaw-gateway.service.status.txt
  - Active: inactive (dead)
  - exited successfully after SIGTERM

This may have been intentional during capture, so it is not by itself a defect. But it means the bundle is a mixed-state capture, not a clean steady-state production snapshot.

Operational implication:
Any claim of current health must be limited to the time window before the stop. The bundle should not be interpreted as proving stable steady-state operation after 14:59.

10. The source tree and live runtime are not yet one truthful system.

The strongest evidence in this bundle is not a single crash. It is the mismatch between:
- committed source service files
- deployed systemd units
- OpenClaw runtime config
- OpenClaw doctor guidance
- actual gateway and Discord runtime behavior

Operational implication:
The project is still in a dual-truth state. That is exactly the kind of condition that keeps engineering teams stuck in harness work instead of returning to the main product.

What this means for the platform verdict

This bundle lowers confidence further in any claim that the harness is finished.

The platform is still not operationally complete because:
- deployment does not match source remediation
- OpenClaw still carries inline secrets in live config and unit state
- session routing is still too permissive and not clearly scoped
- Discord gateway health is unstable
- tool and trust boundaries are too broad
- at least one likely port collision exists
- the runtime topology is still not converged enough to be boring and reliable

Updated verdict

Use this as the current position:

The harness plus OpenClaw stack is partially delivered and actively useful, but it is not yet a finished platform. The live system still shows deployment drift, security debt, session-model ambiguity, gateway instability, and configuration conflicts. It should be treated as a stabilization program, not as a completed operational foundation.

Minimum actions implied by this bundle

1. Eliminate deployment drift.
   - Reconcile deployed systemd units with the remediated source tree.
   - Verify the live openclaw-gateway.service matches the committed service file.

2. Rotate compromised or exposed secrets.
   - Anything present inline in the captured unit/config should be treated as exposed.

3. Redesign the OpenClaw secret model.
   - Remove runtime API keys and tokens from openclaw.json.
   - Move to host secret files or a proper secret store.

4. Resolve the 18791 port conflict or ambiguity.
   - Browser control and Linear webhook cannot share the same stable loopback port on one host.
   - Assign explicit, non-overlapping ports and verify with live listeners.

5. Lock down hook and session routing.
   - Disable arbitrary request-supplied session keys, or strictly prefix-gate them.
   - Set hooks.defaultSessionKey and allowedSessionKeyPrefixes.

6. Reduce gateway tool exposure.
   - Remove shell and other high-risk tools from gateway HTTP exposure unless there is a very strong reason to keep them.

7. Stabilize Discord gateway health.
   - Investigate stale-socket restarts and repeated reconnect cycles before treating Discord as reliable ingress.

8. Align the OpenClaw and harness session model.
   - One session identity, one thread identity, one durable mapping story, end to end.

Bottom line

feedback2 should conclude that the OpenClaw debug bundle does not rescue the delivery verdict. It makes the remaining problems more concrete. The system is real and doing work, but the live operational stack is still not converged, not safely hardened, and not ready to be called finished.
