## 1. Executive Verdict

The harness is **partially delivered**. The updated source shows real remediation work and a materially better runtime than before, but it is **not yet fully functionally delivered as a reliable autonomous platform**. The overall approach is **sound in concept but still overcomplicated in execution**. The methodology is **viable only with further hardening, simplification, and truth-aligned operational controls**. The team should **stabilize and reduce this harness**, not keep expanding it in its current shape.

## 3. Real Architecture Summary

The actual implemented architecture is a **multi-service control plane plus worktree execution plane**.

The **control plane** is:

* `anqr-linear-webhook.service` on port `18791`
* `anqr-discord-router.service` on port `18790`
* `anqr-symphony-router.service` on port `4319`
* `anqr-symphony-integrator.service`
* `anqr-symphony-worktree-recovery.service`
* `anqr-watchdog.service`
* `openclaw-gateway.service` on port `18789`
* support services `anqr-context7-mcp.service`, `litellm-proxy.service`, `model-injector-proxy.service`

The **execution plane** is:

* `anqr-symphony-executor@1..8.service`
* worktree-local execution through `harness/ops/integrations/model/symphony-openai-bridge.mjs`
* Linear work reserved to `wt1-wt4`
* Discord work reserved to `wt5-wt8`

The **real critical coupling points** are:

* `harness/ops/lib/durable-kv.mjs`
* `harness/ops/core/task-evidence.mjs`
* `harness/ops/symphony-state.mjs` and `harness/ops/core/symphony-state/*`
* `harness/ops/integrations/model/symphony-agent-router/*`
* `harness/ops/integrations/model/symphony-openai-bridge/server.mjs`
* `harness/ops/orchestration/symphony-runner/execute-issue.mjs`
* `harness/ops/orchestration/symphony-integrator/integrate-candidate.mjs`

This is **not a clean hexagonal runtime**. It is an orchestration-heavy runtime with partially separated adapters. The codebase has boundary intent, but the live runtime still couples transport, provider selection, notifications, evidence, worktree mutation, and integration behavior more tightly than the doctrine suggests.

## 4. End-to-End Flow Assessment

### Discord/OpenClaw to router to executor

**Intended flow**
OpenClaw should forward Discord requests into the Discord router, which should preserve session and thread context, route to `wt5-wt8`, and keep follow-up turns on the same worktree and Discord thread.

**Actual implemented flow**
`openclaw-gateway.service` feeds `anqr-discord-router.service`. `discord-request-router/server.mjs` accepts `x-openclaw-session` or `x-openclaw-session-key`, chooses a worktree through `getLeastLoadedWorktree(sessionId)`, then `process-and-proxy.mjs` forwards the request to the executor bridge. Evidence is created at ingress. Thread naming is derived from `getSessionThreadName()` and forwarded as `x-discord-thread-name`.

**Verified files/services**
`services/systemd/openclaw-gateway.service`
`services/systemd/anqr-discord-router.service`
`harness/ops/integrations/model/discord-request-router/server.mjs`
`harness/ops/integrations/model/discord-request-router/process-and-proxy.mjs`
`harness/ops/integrations/model/discord-request-router/get-least-loaded-worktree.mjs`
`harness/ops/integrations/model/discord-request-router/session-thread-names.mjs`
`harness/ops/integrations/model/symphony-openai-bridge/server.mjs`

**Failure points**

* `server.mjs` accepts `x-openclaw-session-key`, but `process-and-proxy.mjs` only reads `x-openclaw-session`
* `symphony-openai-bridge/server.mjs` also only reads `x-openclaw-session`
* sticky session/thread state is stored in in-memory `Map`s, not durable state
* Discord preview sanitization does not remove the “Sender (untrusted metadata)” / “Untrusted context” style content shown in your runtime sample
* user-visible provider fallback messages are too noisy

**Verdict**
**Partially delivered. Operationally fragile.**

### Linear webhook/export/guardian flow

**Intended flow**
Linear should deliver issue events by webhook, dedupe them durably, route them into the Symphony router, execute them on `wt1-wt4`, and maintain an auditable correlation trail.

**Actual implemented flow**
`linear-webhook-receiver/handle-webhook.mjs` verifies signature, dedupes by `linear-delivery`, creates an evidence record, and calls `triggerIssueExecution(processedEvent, correlationId)`. That posts to `/v1/linear/trigger` on the Symphony router. The router extracts the correlation ID and may queue or dispatch.

**Verified files/services**
`services/systemd/anqr-linear-webhook.service`
`harness/ops/integrations/model/linear-webhook-receiver/handle-webhook.mjs`
`.../verify-signature.mjs`
`.../recent-deliveries.mjs`
`.../active-issues.mjs`
`.../trigger-issue-execution.mjs`
`harness/ops/integrations/model/symphony-agent-router/handle-linear-trigger.mjs`
`.../dispatch-linear-execution.mjs`

**Failure points**

* `verify-signature.mjs` returns `true` when the signature is missing or the secret is absent
* `dispatch-linear-execution.mjs` drops `correlationId` after `handle-linear-trigger.mjs` extracts it
* durable dedupe and queue state are file-backed but not safely concurrent

**Verdict**
**Partially delivered.**

### Worktree provisioning and execution flow

**Intended flow**
Worktrees should be isolated, health-checked, recovered safely, and validated against mainline without destructive behavior.

**Actual implemented flow**
Executors run in `%h/src/anqr-wt%i`. Validation sync in `sync-worktree-before-validation.mjs` now uses fetch, stash, and rebase rather than reset/patch. Watchdog and recovery can quarantine worktrees instead of hard-resetting them.

**Verified files/services**
`services/systemd/anqr-symphony-executor@.service`
`services/systemd/anqr-symphony-worktree-recovery.service`
`harness/ops/orchestration/symphony-runner/sync-worktree-before-validation.mjs`
`harness/ops/orchestration/symphony-runner/execute-issue.mjs`
`harness/ops/runtime/symphony/watchdog-monitor/quarantine-worktree.mjs`

**Failure points**

* bridge-to-runner layering remains complex
* stash and rebase remain operationally subtle
* worktree lifecycle is spread across runner, watchdog-monitor, recovery daemon, and core state

**Verdict**
**Delivered but operationally fragile.**

### Provider routing and fallback flow

**Intended flow**
Provider selection should be health-aware, auditable, and recover gracefully from provider-specific failures without degrading the user experience.

**Actual implemented flow**
The bridge uses the Symphony credit gate and provider probing. Some providers are explicitly rejected when they emit malformed tool-call output. Your sample `RAW_TOOL_JSON_TEXT` Cerebras failure matches the explicit rejection path in `invoke-with-aiinner.mjs`.

**Verified files/services**

`harness/ops/integrations/model/symphony-openai-bridge/server.mjs`

**Failure points**

* provider selection evidence is not joined to task evidence
* the structured logging/evidence layer for provider choice is mostly not wired into runtime transitions

**Verdict**
**Delivered but operationally fragile.**

### Queue control and recovery flow

**Intended flow**
Queue state should survive restarts and concurrent activity, and recovery should be safe and observable.

**Actual implemented flow**
The old in-memory queue has been replaced with `createDurableQueue("symphony-linear-queue")`, and watchdog behavior now prefers restart and quarantine rather than destructive rollback. Recovery daemon remains active.

**Verified files/services**
`harness/ops/lib/durable-kv.mjs`
`harness/ops/integrations/model/symphony-agent-router/linear-queue.mjs`

`harness/ops/runtime/symphony/watchdog-monitor/main.mjs`

**Failure points**

* `durable-kv.mjs` has no inter-process lock or atomic compare-and-swap logic
* queue correctness under concurrent writers is not proven
* watchdog comments and some docs still describe rollback behavior that no longer exists

**Verdict**
**Improved, but still unsafe under concurrency.**

### Reporting and evidence flow

**Intended flow**
Each autonomous task should produce a durable, complete audit trail from ingress through routing, provider choice, execution, validation, push, integration, and recovery.

**Actual implemented flow**
Ingress evidence is created in `linear-webhook-receiver/handle-webhook.mjs` and `discord-request-router/process-and-proxy.mjs`. `task-evidence.mjs` supports a full lifecycle model, but almost all lifecycle update functions are unused in live runtime.

* structured logger exists but is not actually adopted across the runtime

**Verdict**
**Partially delivered.**

## 5. Major Findings

### Critical

**1. Durable control-plane state is not safely concurrent**
Severity: Critical
Why it matters: The new dedupe and queue layer can lose updates, double-process, or reorder state under concurrent service activity.
Exact evidence: `harness/ops/lib/durable-kv.mjs` implements `createDurableSet`, `createDurableMap`, and `createDurableQueue` as simple read-modify-write JSON files without any lock. These are used by `harness/ops/integrations/model/linear-webhook-receiver/recent-deliveries.mjs`, `.../active-issues.mjs`, and `harness/ops/integrations/model/symphony-agent-router/linear-queue.mjs`.
Evidence class: Proven
Recommended fix: Move durable-kv onto the existing locked state plane in `harness/ops/core/symphony-state/*`, or add a real inter-process lock and atomic update protocol.

**2. Correlation and evidence are only partially wired through the actual runtime**
Severity: Critical
Why it matters: You cannot claim end-to-end traceability when the control flow drops the correlation ID before executor handoff and the lifecycle recorders are unused.
Exact evidence: `harness/ops/integrations/model/symphony-agent-router/handle-linear-trigger.mjs` extracts `correlationId`, but `dispatch-linear-execution.mjs` accepts only `identifier` and sends no correlation header onward. `harness/ops/core/task-evidence.mjs` defines lifecycle recorders, but runtime usage is limited to `createEvidenceRecord` at ingress.
Evidence class: Proven
Recommended fix: Thread `correlationId` through router dispatch, executor bridge, runner, integrator, and watchdog. Replace “ingress-only” evidence with full lifecycle updates.

**3. Discord session and thread continuity are broken and non-durable**
Severity: Critical
Why it matters: This is user-visible. It breaks conversational continuity and explains the missing Discord thread context you observed.
Exact evidence: `harness/ops/integrations/model/discord-request-router/server.mjs` accepts `x-openclaw-session` or `x-openclaw-session-key`, but `process-and-proxy.mjs` only reads `x-openclaw-session`. `harness/ops/integrations/model/symphony-openai-bridge/server.mjs` also only reads `x-openclaw-session`. Sticky session state lives in `harness/ops/integrations/model/discord-request-router/session-thread-names.mjs` as `new Map()`. Thread cache in `harness/ops/integrations/notifications/openclaw-discord/discord-thread-cache.mjs` is also an in-memory `Map`.
Evidence class: Proven, reinforced by your runtime sample
Recommended fix: Standardize on one session header set, persist sticky session-to-worktree mapping durably, and carry the same session and thread identity through every hop.

**4. Linear webhook signature verification is permissive enough to bypass security expectations**
Severity: Critical
Why it matters: A production webhook receiver should not silently accept missing signatures or missing secrets.
Exact evidence: `harness/ops/integrations/model/linear-webhook-receiver/verify-signature.mjs` returns `true` when the signature is missing or when `WEBHOOK_SECRET` is absent. `webhook-secret.mjs` also falls back to `LINEAR_API_KEY`.
Evidence class: Proven
Recommended fix: Enforce signature verification in production mode and fail closed unless `LINEAR_WEBHOOK_SECRET` is configured.

### High

**5. The new E2E tests are useful live smoke tests, but they do not prove full runtime delivery**
Severity: High
Why it matters: The platform still lacks proof for actual end-to-end execution, provider choice, validation, push, and integration outcomes.
Exact evidence: `tests/e2e/linear-flow.spec.ts` proves webhook ingress, filtering, and evidence creation. `tests/e2e/discord-flow.spec.ts` proves health, routing response, and ingress evidence creation. `tests/e2e/integration-promotion.spec.ts` proves health, queue CRUD, and trigger acceptance. None of these tests verify a full mutation/integration lifecycle to `origin/main`.
Evidence class: Proven
Recommended fix: Add a hermetic full-path suite that verifies executor work, runner completion, validation result, integration queue update, and integrator completion.

**6. Documentation and service comments still materially contradict runtime reality**
Severity: High
Why it matters: Operators cannot safely trust doctrine when root docs and some unit comments describe a different system.
Exact evidence: `services/systemd/anqr-symphony-router.service` header still says `Linear -> Linear Runner -> Symphony Router`, even though active ingress is `anqr-linear-webhook.service`. `services/systemd/anqr-watchdog.service` header still says it “automatically rolls back to previous git commit”. `README.md`, `AGENTS.md`, and `docs/harness/12-concurrent-execution-with-worktrees.md` still contain stale runner, push, and test claims, including references to `anqr-symphony-runner@*.timer`, auto-push to `origin/main`, and “90+ E2E tests”.
Evidence class: Proven
Recommended fix: Rewrite root and harness doctrine from the active service files and code only. Remove or archive stale runner-era guidance.

**7. Direct push to `origin/main` remains a high-risk integration model**
Severity: High
Why it matters: The integrator is still a single automation path that can land code directly on main.
Exact evidence: `harness/ops/orchestration/symphony-integrator/integrate-candidate.mjs` runs `git("push", "origin", "HEAD:main")`.
Evidence class: Proven
Recommended fix: Move to a protected integration branch or merge queue unless there is a strong operational reason not to.

**8. Critical runtime surfaces can still start without required env files**
Severity: High
Why it matters: The services may start partially configured, which weakens the claim that secret loading now fails clearly.
Exact evidence: `services/systemd/anqr-symphony-executor@.service`, `anqr-discord-router.service`, `anqr-linear-webhook.service`, `anqr-symphony-router.service, and others use `EnvironmentFile=-...`, which makes the env files optional.
Evidence class: Proven
Recommended fix: Make required env files mandatory for critical services, or add explicit startup validation that fails closed when required secrets are absent.

## 6. Architecture Assessment

**Hexagonal integrity**
Partially present. The code shows clear intent to isolate adapters and maintain contract boundaries, but the runtime still couples transport, orchestration, notifications, provider routing, and git mutation too tightly.

**Contract enforcement**
Better than average. There are meaningful checks, typed configs, dependency rules, and service separation. But runtime truth still diverges from the stronger contract story in docs.

**Adapter boundaries**
Improved, not clean. OpenClaw, Discord, provider routing, and runner behavior still bleed across each other in `symphony-openai-bridge/server.mjs`.

**Orchestration design**
Capable, but over-layered. Router, executor bridge, runner, integrator, watchdog, recovery, and dual state systems create a lot of moving parts.

**Service decomposition**
Mostly reasonable. The split between ingress, execution, integration, and support services is sensible. The problem is overlap and drift, not service count alone.

**Worktree strategy**
Good concept. `wt1-wt4` for Linear and `wt5-wt8` for Discord is a sensible separation. The weak point is preserving safe and durable identity, concurrency, and recovery around that scheme.

**Systemd strategy**
Appropriate overall. The units are materially better now. Remaining problems are optional env loading on critical services, stale comments, and some lingering mismatch between doctrine and service truth.

**AI orchestration methodology**
Viable, but not yet production-grade. Provider routing is sophisticated. The traceability, session continuity, and runtime proof are not strong enough yet.

**Operational simplicity versus accidental complexity**
The harness still leans too far toward accidental complexity. The bridge-to-runner split, custom state layers, and large documentation surface continue to cost more than they return.

## 7. Logging and Observability Assessment

**What is good**

* correlation IDs now exist as a concept
* ingress evidence records are created for Discord and Linear
* health endpoints exist on major services
* worktree identifiers are visible in service naming and many logs
* watchdog behavior is safer than before

**What is missing**

* full lifecycle evidence updates
* consistent use of structured logging
* durable session and thread identity
* correlation propagation into all execution and integration hops
* provider-choice evidence tied to task evidence
* integration evidence tied to the same task correlation ID

**What is dangerously missing**

* a single authoritative audit trail for one task from ingress to integration
* reliable explanation of which provider handled a specific Discord or Linear task
* durable reconstruction of sticky-session routing after router restart
* safe concurrency semantics for the new durable control-plane files

**Whether incident reconstruction is realistically possible**
Only partially. An operator can reconstruct ingress and some routing from logs plus evidence files, but not a full trustworthy lifecycle for many tasks.

**Required logging improvements**

1. Use `createStructuredLogger()` across router, bridge, runner, integrator, and watchdog.
2. Carry `correlationId` into `dispatch-linear-execution.mjs` and the executor bridge.
3. Record worktree selection, provider selection, execution result, validation result, push result, and integration result through `task-evidence.mjs`.
4. Add consistent fields: `correlationId`, `service`, `worktreeId`, `issueIdentifier`, `providerName`, `route`, `attempt`, `stateTransition`.
5. Log session key and Discord thread linkage in one durable place.

**Required evidence/reporting improvements**

1. Make `task-evidence.mjs` the actual authoritative record, not just an ingress file.
2. Record watchdog interventions into task or worktree evidence.
3. Record integrator outcomes with the originating correlation ID.
4. Add queue decision records for queued, dropped, requeued, and dispatched events.
5. Add an operator command that reconstructs one task from evidence only.

## 12. Go / No-Go Recommendation

**Is the harness ready to be treated as operational?**
**No-Go** for a fully autonomous, production-trustworthy platform.

**Should the team continue investing in it in its current form?**
Not in its current form. The right move is controlled hardening and simplification, not more feature growth.

**Should the architecture be simplified?**
Yes. Keep the worktree split, provider routing, ingress services, and integrator. Reduce state duplication, fix identity propagation, and tighten the execution contract.

**Minimum set of fixes before the team can safely return focus to the main project**

1. make durable control-plane state safe under concurrency
2. fix Discord session/thread continuity end to end
3. propagate correlation IDs through execution and integration
4. wire real lifecycle evidence, not ingress-only evidence
5. enforce webhook signature verification in production
6. remove stale doctrine and serviime
7. prove one full Discord flow and one full Linear flow with real automated tests

Until those are done, the harness will still consume time through uncertainty, user-visible odd behavior, and partial observability.
